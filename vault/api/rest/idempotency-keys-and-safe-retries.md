# Idempotency keys and safe retries

A client sends a POST to create a payment. The connection drops
before any response comes back. The network cannot tell the client
whether the server received the request, processed it, and simply
failed to deliver the response, or never saw it at all.

That leaves the client with two options, and both are risky on their
own. Retrying the POST risks creating a second payment if the first
one actually went through. Not retrying risks losing the payment
entirely if it didn't. Neither option is safe by itself, because POST
carries no guarantee that repeating it leaves things as they were.

Given that a client cannot tell whether a dropped connection means its POST was processed or not, why is neither "always retry" nor "never retry" a safe default? :: Always retrying risks performing the operation twice if the original request actually succeeded server-side before the connection dropped. Never retrying risks losing the operation entirely if the request never reached the server or was never processed. Without more information, either choice can produce the wrong outcome for the client's actual intent. ^card-g31c

An ==idempotency key== is the fix: a unique value the client ^card-rfsg
generates itself and attaches to the request, meant to identify one
particular attempt at "create this payment" so that sending the same
attempt twice is recognizable as the same attempt rather than two
separate ones.

That key has to come from the client rather than be assigned by the
server, because only the client knows which two HTTP requests
represent a single intended operation. From the server's side, two
POSTs with identical bodies arriving seconds apart look exactly like
two customers coincidentally paying the same amount — nothing about
the request itself says "this is a retry of that other one." The key
is the client attaching that knowledge to the request explicitly.

Why must the idempotency key be generated by the client rather than handed out by the server on an earlier response? :: Only the client knows whether a given request is a fresh operation or a retry of one it already attempted — the server has no way to distinguish a retry from a coincidentally identical new request by looking at the request alone. The key is how the client communicates that intent, so it has to originate wherever that intent lives. ^card-wixc

On seeing a key for the first time, the server does the work and
then stores a record of that attempt.

That record holds the key itself, a ==request fingerprint== capturing ^card-95ic
the body that came with it, and the response the request produced.

On seeing the same key again, the server skips redoing the work and
returns the stored response instead. That record has to be kept at
least as long as a client might plausibly still be retrying, which in
practice means some bounded retention window rather than forever.

> [!card] recall
> When a server first processes a request carrying a new idempotency
> key, what three things does it need to store together, and roughly
> for how long? What does it do differently the next time it sees
> that same key?
> ---
> It stores the key, a fingerprint of the request body that came with
> it, and the response the request produced. That record is kept for
> a bounded retention window — long enough to cover realistic retry
> delays, not indefinitely. On seeing the same key again within that
> window, the server does not repeat the work at all; it just returns
> the stored response from the first attempt. ^card-exra

The stored fingerprint exists for a reason beyond bookkeeping: it
catches a client sending the same key with a genuinely different
body.

> [!card] mcq
> A second request arrives reusing an idempotency key from an earlier
> request, but its body differs from what that key was originally
> recorded with. What should the server do?
> - [x] Reject it as a client error — reusing a key for a different request body is a bug, and the request must not be silently served the earlier response
> - [ ] Serve the stored response from the original request, since the key matched
> - [ ] Process the new body normally and overwrite the stored response under that key
> - [ ] Merge the two request bodies and process the combination ^card-cj4s

There is one more failure mode worth naming: two requests carrying
the *same* key arrive concurrently, before the first one has
finished being processed and before any response has been stored yet
for the second to find. If the server doesn't guard against that
overlap, both requests can slip past the "have I seen this key
before?" check at the same moment and both end up doing the work.

How must a server handle two requests with the same idempotency key that arrive concurrently, before either has finished processing? :: It must serialize them around that key — for example by having the second one block until the first finishes and then reuse its stored result, or by having the second one reject with a conflict — rather than letting both pass the "is this key new?" check at once and both perform the operation. ^card-ohx8

This whole mechanism is what lets POST behave idempotently in
practice — but that guarantee is achieved deliberately, through the
key, fingerprint check, and stored-response lookup described above,
rather than existing by definition the way it does for other methods.

What is the difference between the idempotency an idempotency key gives POST and the idempotent guarantee GET or PUT already has by definition? :: GET and PUT are idempotent as part of their HTTP semantics, with no extra machinery required to make repeating them safe. POST has no such built-in guarantee; an idempotency key only makes it behave idempotently at the application level, and only for as long as the key, fingerprint check, and stored-response lookup described above are actually in place — remove that machinery and POST loses the guarantee entirely. ^card-j73k
