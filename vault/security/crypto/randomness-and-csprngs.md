# Randomness and CSPRNGs

Every key, nonce, and IV in cryptography ultimately traces back to a
random number generator, and the previous note's Kerckhoffs's-principle
point — the key is the only secret — means the *quality* of that
randomness is doing all the work. A perfect cipher fed a predictable
key is not a perfect cipher; it's a puzzle.

**Entropy** measures how much genuine unpredictability a source
contains, in bits — not how long or complicated a value looks. A
64-character string generated by hashing the current timestamp can look
impressively random while containing only a few dozen bits of entropy,
because an attacker who guesses the timestamp's rough range can
regenerate the whole string. Entropy has to come from something the
attacker cannot observe or predict, such as hardware timing jitter,
thermal noise, or dedicated hardware random-number generators.

Why can a long, complex-looking value still have very little actual entropy? :: Entropy measures the attacker's uncertainty about the value, not its length or apparent complexity. If the value is derived deterministically from something narrow and guessable — a timestamp, a process ID, a counter — an attacker who searches that narrow space can reconstruct it, regardless of how random the final string looks after hashing or encoding it. ^card-4k1m

A **PRNG** (pseudorandom number generator) stretches a short seed into a
long stream of numbers that pass statistical randomness tests, but it
gives no guarantee about *predictability* to an adversary — many PRNGs,
like the Mersenne Twister used in most languages' default `random()`,
are built purely for statistical quality and speed, not for resisting
an attacker who's trying to guess the next or previous outputs.

A stronger generator adds exactly the guarantee a plain PRNG lacks:
given any prefix of its output, an attacker with realistic computing
power cannot predict the next output, nor recover earlier outputs by
working backward. That forward- and backward-unpredictability is the
entire difference between an ordinary PRNG and a ==CSPRNG== (short for ^card-xfr3
cryptographically secure PRNG) — statistical randomness is necessary
for both but sufficient for neither, on its own, to justify using the
output as a cryptographic key.

Why is a language's default `random()` function unsafe for generating a cryptographic key, even though it produces statistically well-distributed output? :: Because the default generator is typically a plain PRNG optimized for speed and statistical quality, not for resisting prediction. Its internal state is small enough, and its output sequence structured enough, that observing a handful of outputs lets an attacker reconstruct the internal state and predict every future (and often past) output — which for a key means the attacker can derive it directly instead of brute-forcing it. ^card-eem3

On Linux, `/dev/urandom` and `/dev/random` draw from the same underlying
entropy pool, but they behave differently once that pool has been
initialized: `/dev/urandom` always returns output immediately, reusing
the pool through a CSPRNG construction, while `/dev/random` can block,
waiting for the kernel to judge that enough fresh entropy has
accumulated before it will hand out more bytes.

A CSPRNG's entire output stream is only as strong as its seed. If the
seed is guessable, predictable, or reused across two independent
instances, every value the generator ever produces — every key, every
nonce it derives — is compromised, even though the algorithm stretching
that seed is perfectly sound.

What goes wrong if a CSPRNG is seeded before the system has gathered enough real entropy, for instance immediately at boot on a device with no hardware entropy source yet? :: The generator's internal state ends up drawn from a small, possibly guessable space, so an attacker can brute-force or predict the seed itself. Every output the CSPRNG ever produces from that seed — keys, nonces, session tokens — inherits that weakness, no matter how cryptographically sound the stretching algorithm is, because the algorithm's strength assumes a high-entropy seed to begin with. ^card-nbxn

Three cryptographic values are all described loosely as "extra random
input," and conflating them causes real bugs: nonce, IV, and salt.

A **nonce** ("number used once") must be ==unique== per key — it must ^card-qyu6
never repeat under the same key, but it does not need to be
unpredictable, and in some schemes it's just a counter.

An **IV** (initialization vector), used by modes like CBC, has a
strictly stronger requirement: it must be hard for an attacker to guess
in advance, not merely distinct from every other value used with that
key, or the encryption mode's security guarantee falls apart entirely.

A **salt**, used to make password hashes come out differently per
user, has the loosest requirement of the three — it only needs to
differ across users. It carries no secrecy or guessability requirement
at all, and can sit right next to the password hash in plaintext.

> [!card] recall
> Nonce, IV, and salt are all "extra input" alongside a key or

> ---
> Salt: merely distinct across uses (public, no secrecy or

> like CBC): unique AND unpredictable to an attacker ahead of time —
> reusing the uniqueness requirement of a nonce isn't enough, since a
> predictable IV lets an attacker mount a chosen-plaintext distinguishing
> attack before the ciphertext is even produced. ^card-adkd
